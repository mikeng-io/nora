# DeepSeek V4.1 Flash context-router probe — 2026-10-07

Executed on norty through OmniRoute's localhost OpenAI-compatible endpoint, with the explicit catalogued route `ollamacloud/deepseek-v4.1-flash`. Responses identified their model as `deepseek-v4.1-flash`; all 24 final response headers reported `x-omniroute-provider=ollamacloud` and `x-omniroute-cache=MISS`. Existing credentials were used on norty, without exporting their values. Nora source and live config were not changed; this is a standalone synthetic probe.

## Method

Reused the same eight generated, pre-labelled situations and routing-state fields as the Tev1 test: English/Cantonese documents, English/Cantonese personal recall, computer task, subagent task, greeting, and old-thread transcript. Identical four block descriptions and depth criteria. A general chat model needs a serialization instruction in place of System One's typed API: return exactly `blocks` and `transcript_window`, with no extra keys, explanation or tools. The saved system instruction and script specify the exact output contract. Requests used temperature 0, reasoning_effort none, max_tokens 256 and nonstreaming completion. No JSON-format API parameter was assumed, since Ollama Cloud documents structured outputs as unsupported. Every response was strictly parsed and validated locally; no repair or retry hid a failure.

First attempt repeated the identical eight inputs three times. The last two passes returned approximately 20ms responses with identical completion IDs and created times to the first pass: this is response reuse, not a valid inference-latency measurement. That exploratory data is retained in cached-repeat-result.json and excluded from the reported latency.

The final run added a unique UUID to each routing state, explicitly marked irrelevant to selection, so each of 24 requests had distinct input. All 24 returned distinct completion ID/created-time pairs. Shared prefix caching may still occur, as it would in normal operation. Timing covers the full norty-to-OmniRoute-to-provider completion and response JSON decoding (plan validation follows the timer), unlike the T4 measurements which exclude WAN transport.

Each pass was 40/40 decisions correct across the eight cases; Tev1 4B's earlier single pass was 38/40, with the two errors in depth. Repetition does not create 24 independent scenarios: there are still only eight distinct cases, and 100 percent here is not Nora deployment accuracy. Model confidence calibration was not tested. Inputs are short and their cues explicitly describe which optional context is available; ambiguous mixed-domain or long real-context decisions remain unmeasured.

Completions used 13–16 reported output tokens. Provider usage fields are saved in result.json; no incremental subscription cost was inferred from token counts. This does not use System One's probabilities; the output is a generative ContextPlan, validated by the caller.

## Comparison and recommendation

The relevant measured latencies are 4.103 seconds for Tev1 4B on the Radeon 680M, 1.220 seconds for the first warm pass on T4 (0.842 for repeats), and 1.305 seconds end to end for Flash with distinct inputs. These are microbenchmarks with different execution runtimes and serialization; the Flash result supports it as the next context-exposure candidate, not a promise of sub-second or steady tail latency.

Before integration, compare full-context Nora, a conservative deterministic plan and Flash-selected exposure using the existing anchored replay/eval mechanism. Measure required-context misses, downstream reply quality, total reply latency, and cached/uncached prompt cost. Phase 1 should keep retrieval unchanged; keep transcript depth deterministic initially despite this tiny test's success. Timeout, API error or invalid plan preserves the current full context. ContextPlan remains separate from EngageDecision. Do not make the router a second answer-writing agent.

All requests completed and the standalone probe process exited. No deployment or persistent router process was started.

# Media objects — one content-addressed index, per-resolver scope

**Status:** Proposed (nothing built yet)
**Date:** 2026-08-26
**DEC:** 138 (indexed at the bottom of this document)
**Branch:** `feat/media-architecture` (worktree)
**Supersedes:** DEC-137's storage half (generated-images-library-as-own-table);
extends DEC-24 (conversation media refs), DEC-43 (handle markers); absorbs
migration 0031.

## 1. What this is

One content-addressed **media index** for everything Nora can hold bytes for:
inbound photos, generated images, fetched attachments, and (explicitly in the
design) future generated video/sticker/audio. The index is a single table,
`media_objects`; **`source` is an attribute, not a table**. Tools stay few and
share one resolver; **scope is enforced per resolver, not per store**.

This replaces the shape the last two rounds of work converged on, where each
acquisition path grew its own table (`media_descriptions`, `generated_images`)
and its own tool family (`media_fetch`, `images_lookup`, `images_resend`).
Miles's direction, 2026-08-26: *"呢個係 architecture 嘅問題，而唔係不斷去加
tools 落去"* — a generated image is not a new data type, it is the SAME byte
object with a `source='generated'` row.

## 2. Why the current shape is wrong

Three separate mechanisms currently encode ONE distinction — "what may this
resolver see?" — by splitting tables and tools:

| Layer | Conversation media | Generated library |
|---|---|---|
| Bytes | rustfs blob_store (content-addressed) | rustfs blob_store (content-addressed) |
| Metadata | transcript `media_json` (list of `MediaBlob` per row) | `generated_images` table (prompt/title/…) |
| Description | `media_descriptions` (vision cache, keyed sha256) | (none — regenerated on demand) |
| Tools | `media_fetch` | `images_lookup` / `images_resend` |

Consequences, already visible:

1. **Same concept, three vocabularies.** A handle (`a3f2c1`) is a 6-hex prefix
   of the SAME sha256 in both worlds, but the model is told two different tool
   families exist. Confusion was the first symptom the operator reported.
2. **Scope is welded to schema.** `media_fetch` is conversation-scoped
   (R-21/DEC-24 privacy: Nora must not describe group A's photos in group B),
   but that scope is enforced by *where the rows live*, so a global search
   (`images_lookup`) needs its own table to exist. The privacy property is
   authorization, not storage.
3. **Description acquisition is duplicated.** Inbound bytes need a vision call
   (nobody knows what a stranger's photo shows); generated bytes DO NOT — the
   creator holds the prompt, which IS a description. Current code writes
   `description=prompt` into `generated_images` at generation time
   (`tools.py:3384`) but that row is NOT the `media_descriptions` cache
   `media_fetch` consults, so the first `media_fetch` of a generated image
   still misses the cache and burns a vision call to re-read what Nora
   already knows. Waste, and a semantic lie: a generated image is a
   *creator-known artifact*, not an *unknown inbound object*.
4. **Video (asked for explicitly, "assume it exists") would add a third
   table and a third tool family.** Each new modality repeating table + tool
   + lookup + search is the whack-a-mole Miles called out.
5. **Two known bugs came from this split** (reported 2026-08-26): `images_resend`
   picks `next(...)` on a 6-hex prefix collision where `media_fetch` returns
   `ambiguous`; `images_resend` resolves handles against only the 100 most
   recent rows.

## 3. The unified shape

```
media_objects (one table)
  sha256        PK — the content address; its first 6 hex chars are the handle
  media_type    image | video | sticker | audio | file  (LLM-visible modality)
  size          bytes
  source        inbound | generated | fetched        (WHO brought it in)
  description   text — see §4 for provenance rules
  describe_model  text — which describer produced the description (NULL if seeded)
  provenance    JSONB — source-dependent:
                  inbound:  sender_platform, sender_id, conversation_id
                  generated: prompt, title, description, provider, model,
                             aspect_ratio, platform, conversation_id
                             (all NOT NULL columns today — migration must
                             not drop them; schema.py:1628-1629)
                  fetched: url, identifier
  created_at_ms ms-epoch (sibling of messages.ts; plain int join;
                  converts media_descriptions.created_at DateTime)

  CONSTRAINT: one row per sha256 — the first source to store identical
  bytes wins; a second source sees the existing row and does NOT overwrite
  provenance (merge semantics). Description is a pure function of content,
  so a later describer may refresh `description`/`describe_model` without
  touching provenance.

media_descriptions  ─► folded INTO media_objects (description column)
generated_images    ─► folded INTO media_objects (source='generated' rows;
                       provenance JSON carries prompt/title/description/…)
sticker_index       UNCHANGED — the sticker DEDUP identity layer
                       (platform, fetch_token) → sha256. It lives beside
                       media_objects, never inside it: an identity is NOT a
                       media object. `SqlMediaDescriptionStore.remember`
                       writes BOTH levels in one transaction today
                       (media_descriptions + sticker_index); after the merge
                       it writes (media_objects + sticker_index) in one
                       transaction — sticker sightings become
                       source='inbound' rows with their description, and the
                       content-level dedup (a sticker later media_fetch'd by
                       handle shares one description) is preserved exactly.

transcript media_json  UNCHANGED — it is the per-conversation REFERENCE list
   ("which blobs appeared in this conversation's rows"), not a copy of the
   objects. A generated image delivered to a chat gets its MediaBlob in that
   row's media_json exactly as it does today, and one row in media_objects.
```

**Inbound write path (M4 — the current custody stage writes NO metadata row,**
`nora/ingest/stages/media.py` — it writes media_json + blob bytes only):
ingest MUST gain a `source='inbound'` media_objects row (platform,
sender, conversation_id provenance), otherwise `media_objects` would be a
description-only index and `media_search` could not see inbound photos even
where it legitimately could. This is an ADDITION to the ingest path, not a
replacement: the media_json reference list stays the ingest's transcript
record; media_objects is the object store behind it.

**Why a single table beats a view:** the two existing tables share the primary
key (sha256) and differ only in columns — a view would join one-to-one and
still require the two writes. The merge is a migration that renames
`generated_images` rows into `media_objects` provenance, and copies
`media_descriptions` rows into the same table. Zero generated-image data
exists yet (the table is one test row, deleted); `media_descriptions` has real
rows that migrate in place.

**Marker syntax stays `[image <hex>]`** (DEC-43): the marker is an LLM-facing
modality label ("this is an image"), not a storage state. Future modalities
get their own labels (`[video <hex>]`, `[sticker <hex>]`), all resolving
through the same index. Miles: "more clear [sticker] [video] etc — not for
state but for llm".

## 4. Description provenance — known at creation, learned at first sight

A description is a pure function of the bytes (DEC-24 already keyed
`media_descriptions` on sha256 for this reason). What varies is WHEN Nora
can know it:

| source | description at | cost |
| --- | --- | --- |
| inbound | first `media_fetch` (vision describer) | one vision call, cached forever |
| generated | generation time — the prompt IS the description | zero |
| fetched | first `media_fetch` (vision describer) | one vision call, cached forever |

The `description` column plus `provider`/`model` (who wrote it) keeps the
existing invariant that the identifier screen (`scan_identifiers`) runs on
every serve, cache hit or not.

For generated images the tool writes `description = prompt` at creation; if
Miles later wants richer copy (title/description beyond the prompt), that is an
edit surface on the row, not an architecture change.

**Seeded descriptions are served content.** Once `description=prompt` lives in
`media_objects`, `media_fetch` may serve it — and today the prompt is NOT
screened at generation time (`tools.py:3209-3465` has no `scan_identifiers`
call; it only reaches the provider). The serve-time screen is the ONLY
barrier, so the implementation MUST route every serve — including a
seeded/prompt-sourced hit — through the same `_serve_media` path that runs
`scan_identifiers` on every serve (cache hit or not, `tools.py:3175`), never
around it. A seeded description must not become a fast path that bypasses
the identifier screen.

## 5. Resolver scope — one store, per-resolver authorization

The store is global (one index). The AUTHORIZATION is a property of the
resolver — the filesystem analogy: one disk, but users don't read each other's
home dirs. This is what "per-tool scope rules" means.

| Tool | Scope | Rule |
| --- | --- | --- |
| `media_fetch <handle>` | **conversation-scoped** | only blobs referenced by THIS conversation's rows (`media_json` scan, R-21/DEC-24 unchanged — the privacy boundary is preserved) |
| `media_search <query>` | **custody-scoped, global** | only `source IN (generated, fetched)` — Nora's own media; never inbound rows (other people's photos are not her library). **Amended in part 2026-10-01 (DEC-248): this is the default `library` scope; a second `room` scope also finds photos people sent in the calling room, found through that room's own message rows.** |
| `media_send <handle>` | **custody-scoped** | only `source IN (generated, fetched)` — she cannot forward bytes she does not hold |
| `media_generate` | N/A | the only creation entry; on success writes object + description + delivers |

Miles explicitly approved `media_search` being global: "media_search — yes".

The existing `images_lookup`/`images_resend` tools are replaced by
`media_search`/`media_send` with `source='generated'` as the default scope —
no separate code path.

## 6. Video (and future modalities) falls out

A generated video is the same flow: bytes → sha256 → `media_objects`
(`source='generated'`, `media_type='video'`, provenance prompt/model) →
`[video <hex>]` handle → `media_send` attaches it. The only NEW pieces are
platform-specific (a video describer for `media_fetch`, Signal size limits) —
modality work, not media-architecture work. No new table, no new tool family,
no new resolver. **This is the test the design must pass**: "add video" must
be smaller than "add image" was.

## 7. Supersession chain

- **Supersedes the storage layer of DEC-137** (image generation): the
  `generated_images` table (migration 0031) folds into `media_objects`;
  the ImageGenerator port, provider-agnostic adapter, and `generate_image`
  tool remain.
- **Extends DEC-24** (`media_json`): the per-conversation reference list stays;
  media_objects is the object store behind it.
- **Extends DEC-43** (handle markers): `[image <hex>]` unchanged; modality
  labels extend to `[video]` etc.
- **Absorbs `media_descriptions`**: same content-keyed description cache,
  moved into the unified row.

## 8. What we are NOT doing

- **Not** a generic blob table with type tags and no columns (yagni — the
  provenance columns are load-bearing for search and audit).
- **Not** a third cache tier: `media_descriptions` moves in, it does not grow.
- **Not** per-modality tool families: `media_fetch`/`media_search`/`media_send`
  are modality-agnostic; the tool DESCRIPTION tells the model which
  modalities each handles.
- **Not** removing the transcript `media_json` — it is the conversation
  reference list and stays exactly where R-21/DEC-24 put it.

## 9. Migration plan

Consumers that must move together (verified against code — Kimi audit
2026-08-26): `SqlGeneratedImageStore`, `SqlMediaDescriptionStore`, the
`generate_image` tool (writes the table, `tools.py:3380`), `media_fetch`
tool, `images_lookup`/`images_resend` tools, composition wiring
(`composition.py:918,1436`), `StickerReader` (reads via
`SqlMediaDescriptionStore`, writes `sticker_index` too), ingest media stage
(`nora/ingest/stages/media.py:69`).

1. `0032_media_objects.py` — create `media_objects`; copy
   `media_descriptions` rows (converting `created_at` DateTime → ms-epoch);
   INSERT generated_images into media_objects (provenance JSON carries
   prompt/title/description/provider/model/aspect_ratio/platform/
   conversation_id — all NOT NULL columns today must survive); ingest gains
   `source='inbound'` writes; `SqlMediaDescriptionStore.remember` re-roots
   its description write to media_objects while keeping `sticker_index`
   in the same transaction.
2. Drop `media_descriptions` (folded); keep `generated_images` as a
   `VIEW` for the one consumer that still reads it (or port it — see §10).
3. Schema parity baseline regen (`scripts/gen_pg_baseline.py`).
4. Port `SqlGeneratedImageStore` → `SqlMediaObjectStore` (same methods:
   `save`/`get`/`search`/`by_prefix`), delete the old store.
5. Tools: `images_lookup`/`images_resend` become `media_search`/`media_send`
   (thin wrappers with the scope filter), `media_fetch` re-roots to the
   unified store + conversation scope. **Rename is NOT free:**
   `nora/agent/dreamer.py:190-196` `UNIT_SAFE_TOOLS` hand-lists
   `"images_lookup"` and `tests/unit/test_tool_registry.py` pins the tool
   names — both move with the rename.
6. Tests: update contract + tool + registry tests; add collision/scope tests
   that currently can't pass in two tables; update `StickerReader` contract
   tests that assert the two-level write.

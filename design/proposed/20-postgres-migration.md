# SQLite → PostgreSQL

Operator decision, 2026-08-07: migrate to PostgreSQL, in the same
`docker-compose.yml`. This document exists because the target is the audit
store that **R-2 and A9 guarantee** — the migration must preserve the record
exactly, and that warrants a spec and a review, not a reflex.

## 0. Why now, and why it is small — corrected in the room

Two things were overstated in conversation and corrected by the operator:

- **"Multi-day migration" was wrong. There is no data migration.** The live
  store is **41 rows, 60 KB.** Nothing is being moved.
- **"It's complicated" was wrong. The store is SQLAlchemy Core.**
  `nora/infra/sql/schema.py` defines the schema as `sa.MetaData` / `sa.Table` /
  `sa.Column`, and `audit.py` uses the async engine over a URL. That is
  database-*portable* by construction: the change is the connection URL and
  driver, not the queries.

And the decisive positive: `audit.py` is **full of WAL single-writer
workarounds** — "WAL permits exactly one writer, so under an N-listener burst
that produced a second contender…". Every one of those exists because SQLite
serialises writers. **PostgreSQL MVCC removes the entire class**, so the
migration *deletes* contention logic rather than adding any. The code gets
simpler.

The trigger is the presence collector (design/19): a **separate entry point**
(`python -m nora.presence`) in the **same codebase** (DDD/CA — one domain + one
infra, two `__main__`s), that must write the record a stateless agent also
reads. Two processes sharing a SQLite *file* across containers is the fragile
thing design/19's review flagged (severity-3). Two entry points sharing a
Postgres *server* is ordinary. So Postgres is not a bolt-on for one feature —
it is the substrate that makes the collector, and any later data service,
trivial.

## 1. Scope — a driver swap behind a port, and one rename

- **The `AuditStore` port is unchanged.** Its interface is what R-2/A9 speak in;
  only `SqlAuditStore`'s engine changes. This is exactly the seam that makes a
  backend swap a composition-root change (CLAUDE.md: a port never gains a second
  impl without a contract suite — the Postgres store passes the SAME
  `tests/contract/` suite the SQLite one does, which is the migration's own
  correctness proof).
- **`sqlite+aiosqlite:///…` → `postgresql+asyncpg://…`** (`engine.py`, one
  function). `uv add asyncpg` (never pip).
- **Delete the WAL apparatus** in `audit.py` — the single-writer serialisation,
  the busy-timeout, the `journal_mode=WAL` pragma hook. Postgres has none of
  these problems. This is the part that makes the diff net-negative.
- **`AuditStore` → `RecordStore` (rename, operator-questioned 2026-08-07).**
  The store holds the conversation *record* — messages, delivery status,
  `person_id`, `quoted_ts` — not a compliance audit log. "Audit" over-specifies.
  Since the migration rewrites `SqlAuditStore` anyway, this is the moment to
  rename (`SqlRecordStore`, `RecordStore` port) rather than churn later.
  Pervasive but mechanical; do it as its own commit within the migration so the
  rename and the engine swap are separately reviewable.

## 2. The genuinely SQLite-specific things that must port

Not zero — this is where the care goes, and where the review must look:

- **The schema-parity gate (DEC-11).** `tests/infra/test_schema_parity.py` reads
  `PRAGMA index_xinfo` — SQLite-only. It must be re-expressed against Postgres
  catalogs (`information_schema` / `pg_indexes`), and it must still assert the
  two things DEC-11 says `alembic check` is blind to: the CHECK constraint and
  the `ts DESC` ordering of `idx_messages_conv_ts`.
- **`idx_messages_conv_ts`** is an expression/ordered index excluded from
  autogenerate on purpose (CLAUDE.md). Its Postgres form is a normal
  `CREATE INDEX … (conversation_id, ts DESC)` — simpler than SQLite's, but the
  hand-written-migration rule still applies: the revision that creates it is
  authored, not autogenerated.
- **`sqlite_autoincrement=True`** on the `id` column → Postgres `SERIAL`/identity;
  SQLAlchemy handles this via dialect, but the schema note must change.
- **Alembic** already speaks Postgres; the migration chain (`0001…0004`) replays
  against it. The `env.py` URL wiring changes.
- **Tests on file-SQLite** move to a **test Postgres** — a compose service or
  a fixture-spun instance. This is the bulk of the mechanical work: every test
  that opens a temp `.db` needs a temp schema/database instead.

## 3. Compose — one Postgres, both entry points

`docker-compose.yml` gains a `postgres` service (there is precedent: Honcho runs
its own Postgres in this stack, so it is not a new class of dependency). Nora
and the presence collector are two services with **different `command:`** over
the **same image and codebase**, both pointing at that Postgres by URL from the
host env (DEC-8: the URL/password names an env var, never inlined).

    services:
      postgres:   # the record + presence + media metadata
      nora:       command: python -m nora
      presence:   command: python -m nora.presence   # design/19, after this lands
      signal-cli: …

The collector is design/19's concern; this document only guarantees the
substrate it needs exists.

## 4. What must be true before it ships

1. The Postgres `SqlRecordStore` passes the **same `tests/contract/` suite** as
   the SQLite one did — the port contract is the correctness proof.
2. The schema-parity gate is re-expressed against Postgres catalogs and still
   catches the CHECK constraint and the `ts DESC` ordering (DEC-11 preserved,
   not weakened — probed by a deliberate drift).
3. `idx_messages_conv_ts` is hand-written in its revision; autogenerate is not
   trusted for it.
4. Every WAL workaround in `audit.py` is DELETED, and a probe shows concurrent
   writers no longer serialise (the thing the workarounds existed for is now
   handled by the engine).
5. The `AuditStore→RecordStore` rename is a separate, complete commit — no
   dangling `Audit` references, GLOSSARY updated.
6. Tests run against a real Postgres (compose service or testcontainer), and the
   four gates are green against it.
7. A one-time load of the 41 existing rows into Postgres is scripted (trivial,
   but it must not be hand-waved — the record is preserved, not abandoned).
8. `docker-compose.yml` has the postgres service, host-injected credentials, and
   Nora reaches it by URL; the deployment is rebuilt and verified live.

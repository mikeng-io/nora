# Every occasion

## 1. The rule, and why it was not a rule

**Operator, 2026-10-01: every agent in Nora must assemble through context
assembly. No exception, or it goes back to the original chaos, everything
built differently.**

`03-sequencing.md` left one question open on purpose: whether a seventh
occasion joins the registry ("should not be swept in silently"). Nothing
answered it, and occasions kept arriving: note-merge (DEC-202), the Instagram
summons, the Cognition session. The census that was meant to hold the line,
`tests/architecture/test_the_registry_is_exhaustive.py`, read a hand list of
five files. **A list of occasions cannot catch an occasion nobody added to
it.** The rest of the architecture suite (`test_one_block_injector.py`,
`test_one_transcript_renderer.py`, `test_one_row_renders_one_line.py`) each
catch one symptom (a hand-written tag pair, a `.body` interpolation, a direct
record read) and a prompt in plain prose that avoids all three passes every
one of them. That is exactly what the Cognition session is.

## 3. Why Cognition fails: its input contradicts its output

Read from the trace of 2026-10-01 09:08 and the code:

- The prompt shows a message as `[#7998]`. `note_create` requires the id as a
  bare `[7998]` and an `(<names>)` attribution (`nora/domain/note_body.py`).
  The tag turn has a remap, `resolve_positions`; Cognition has none, and no
  test passes a rendered id through `note_create`. The session refused three
  times (`section_order`, `uncited`, `misattributed`) before it landed.
- Note-candidates and the curator show `n="<row id>"`, so the id shown is the
  id required. Cognition is the one Dreamer pass that does not.
- The grammar (`(Names)`, `## Owed`, `## Ruled out`) is taught nowhere in its
  objective; the model learns it from refusals. The shared channel for "what
  this block is and how to read it" is the block's type description in
  `nora/domain/block_types.py`; Cognition has no blocks and so no description.
- Group text is not escaped (R-13); the other renderers do.

All four are closed by step 3b (§5): the prompt is blocks, `n` is the row id and
`from` the name the validator compares, the grammar is in the block types, and the
text is escaped.

## 4. The enforcer

`tests/architecture/test_every_model_call_is_a_declared_occasion.py` finds, by
AST and with no list of occasions, every module that calls a model (under the
name it imported the call by) and every class or function that defines
`inputs`, and demands each be declared: a module-level, non-empty `_BLOCKS`
and a call to the `assemble` imported from `nora.domain.blocks`. A module may
also never join rendered blocks by hand (`<name>.render()` or
`map(<x>.render, ...)` handed to a `.join`), anywhere in `nora/` but
`blocks.py`: that is what reverting ONE of a module's several `assemble` calls
writes, and "any call in the module" cannot see it.

**The rule is: no debt ledger, and no exception for an occasion** ([ADR 0021](../../docs/adr/0021-every-prompt-is-assembled-and-the-enforcer-finds-it.md) records why). An occasion
that builds a prompt is declared and assembled, or the test fails. The only
modules that are not occasions are the named MECHANISM, RUNNER and EXEMPT
entries in the test, and they are not a list of exceptions to the rule but a
classification of what is not an occasion, each with a written reason, reviewed
in the PR that adds it and re-checked by the test: the module exists and still
calls a model, a RUNNER's builders exist and are themselves declared, and an
`imports` runner really imports one of them. The classification is a gap a
reviewer can still be argued across (one line in MECHANISM or in a `dispatched`
RUNNER turns a hand-built occasion green, because the test cannot read what the
module does with the prompt it is handed), so adding to it is the one act this
rule asks a human to refuse on sight. What it does NOT allow, and the test
enforces, is anything like the scaffolding of steps 0 to 5: a PENDING table, a
`CEILING`, a `KNOWN_HAND_BUILT` record, or a count of tolerated violations.

Steps 0 to 5 carried that scaffolding while the tree was moved over: a PENDING
ledger (nine entries at the first commit of #675, twelve after its review, none
after step 4c), pinned to an exact size by a `CEILING`, plus a `KNOWN_HAND_BUILT`
table for text found by reading. Step 6 deleted all three, and then the sibling
debt tables that were empty but still open (`HAND_WRITTEN` and
`test_the_census_can_only_shrink` in `test_one_block_injector.py`,
`UNCONVERTED` in `test_one_transcript_renderer.py`, `_NOT_THE_FALLBACK` in
`test_one_name_space_per_prompt.py`, `_NOT_A_BLOCK_TYPE` in
`test_every_block_declares_its_type.py`), each given a positive control so the
test still bites on a synthetic offender. A hand-built text the net cannot see is
fixed, or covered by a purpose-built architecture test, never recorded.

An independent review of the first version (PR #675) found, reproduced and
closed: an `assemble` matched by name alone (a local function or
`ContextAssembler.assemble` passed), an empty or function-local `_BLOCKS`
passing, a runner's named builder never checked against its imports (re-pointing
laundered a debt), a ceiling that was a cap and not a ratchet, aliased and
`self._runner.invoke` doors missed, and prompt text hand-built inside runners
(fire's headers, the debrief's `_prompt`) invisible. The last is not detectable
by the net; steps 2b and 4b to 4c moved each one found into a typed place, and
`test_framing_is_one_typed_place.py` now watches the authored text. The review of
step 6 found the wiring thin (each of these left the file green: dropping
`defines_inputs` from `violations`, dropping the RUNNER builders, skipping the
`imports` check, the raw `completions.create` door, any name from
`domain.blocks` counting as `assemble`, `create_agent` out of the door list);
each now has a test through the real function and a row in
`scripts/mutations/context-assembly-6-close.json`.

**Model doors it sees:** `create_agent`, `create_dream_agent`, `ask_text`,
`ask_structured`, `invoke_async`, `.stream_async`, `.structured_output` and
`.structured_output_async`, `.invoke` on a receiver named `*runner` or
`*factory`, `invoke.run`, `.create` on `completions`, `messages` or `responses`,
and `.complete(system=, prompt=)`.

**What it still cannot see**, stated so review covers it:

- a hand-built text INSIDE a RUNNER, a MECHANISM or an EXEMPT module. A cheap
  test for it was tried and rejected: an f-string of five words or more outside
  a raise, an assert or a log call finds seven hits in those fifteen modules,
  five that are not prompts (the Dreamer's messages about a misdeclared adaptor,
  a regex) and two that are the vision summarizer's own authored hints, so it
  would need a list of allowed sites, which is the thing this rule does not
  have. A new such text is found by a person, who gives
  it a test of its own;
- a model door it does not know: Honcho's `chat` (a dialectic query to a memory
  service's own model), image generation, a positional `.complete(system,
  prompt)`, an alias (`f = factory.invoke; f(...)`), a bare `agent(prompt)`,
  `.invoke` on a receiver not named `*runner` or `*factory`, and
  `evals/rebuilt/grading.py`'s judge (outside `nora/`, which the net does not
  read);
- a model call reached only through an imported helper (the net is per-module,
  with no call graph);
- a `_BLOCKS` walked by `assemble` over a list that does not come from it, and a
  join of blocks written some other way than `.join` over `.render()` (a loop
  with `+=`, `sorted` then concatenation).

## 6. How a new occasion joins

An occasion is any place a prompt reaches a model: an agent turn, a Dreamer pass, a fold, a picker, a summarizer. Joining is the same list for all of them. Each part names the test that fails when it is skipped, and what no test checks.

1. **Declare the table.** A module-level, non-empty `_BLOCKS: tuple[...] = (...)` literal, one row per block (`name`, `order`, `key`, or `source` when one block type appears more than once, as in `nora/domain/summons.py`). The `order` is the order the model reads, which is data and not a comment. Enforced by `test_nothing_builds_a_prompt_outside_context_assembly` (`undeclared`), and the rows are checked against the blocks the module builds, both ways, by `tests/architecture/test_the_registry_is_exhaustive.py`.
2. **Walk it with `assemble`.** Import `assemble` from `nora.domain.blocks` and call it over blocks that come from the table; a join with `"\n".join(b.render() for b in blocks)`, `sorted` or a local function of that name is a hand join. Pass `sep=` for the separator the occasion reads, and `when_empty=` on a block whose empty body must still render (`self_close`, `render`, `nothing`; the default `drop` is right when a body is never empty). Enforced by the same test (`hand_joined` when the module never calls `assemble`, `hand_join_call` for a `.join` over rendered blocks anywhere in `nora/`). **Not enforced:** that the list handed to `assemble` is the one built from `_BLOCKS`, or a hand join spelled some other way than `.join`.
3. **Share the builders.** A block another occasion already builds (`today`, notes, Standing, culture, presence, the self card, the decisions log) comes from its shared builder in the module that owns it, and the caller stamps it with this prompt's own `order` and `key` through `restamp(block, row)`, where `row` is the table's name-to-`(order, key)` mapping; do not write a second builder. Enforced by `test_the_registry_is_exhaustive.py`'s shared-builder list (add a new shared builder there) and by the per-module checks in `tests/architecture/test_one_block_injector.py`, `test_one_transcript_renderer.py`, `test_one_row_renders_one_line.py` and `test_one_name_space_per_prompt.py` (add the module to `CONVERTED` in the first two).
4. **Declare the type.** Every block name has a `BlockType` in `nora/domain/block_types.py`: a description of what the block IS and how to read it, and a gloss for each attribute it can emit. This is the one channel that tells the model what it is reading, so a rule about how to read a block goes there and not into an objective. A type whose two renderers differ in what a field means is two types. Enforced by `tests/architecture/test_every_block_declares_its_type.py`: a block with no type fails, a type nothing renders fails, and a description must describe rather than label. **Not enforced:** that every attribute the renderer can emit has a gloss. Only the Cognition types are held to that (`tests/unit/test_cognition_block_types_explain_every_field.py`), and `tests/unit/test_prompt_documents.py` covers part of the rest, so a new type's glosses are review.
5. **Escape through the shared renderers.** A member's or a stranger's text goes in through `render_rows`, `render_messages`, `render_row_window`, `render_group`, `wrap_outside_text` or `nora.domain.prompt.escape`, never by interpolation, and a speaker is named through `speaker_label`. Enforced in part by `test_one_row_renders_one_line.py`, `test_one_name_space_per_prompt.py` and `test_escaping_is_for_prompts_only.py`. **Not enforced:** a body interpolated into an attribute or an f-string the tests do not read.
6. **Put authored framing text in `nora/domain/framing.py`.** A header, a head paragraph or a closing line is one typed builder there, and every value enters it through `_put` in one of its four named ways; the occasion only names inputs. Enforced by `tests/architecture/test_framing_is_one_typed_place.py` for fire, the announcement, the summons and the prefill; **not enforced** for prose elsewhere (see Open).
7. **Read a Standing or culture head through the withdrawal rule.** `read_culture`, or `render_supported` at the call, or a pinned `RAW` entry with its reason. Enforced by `tests/architecture/test_withdrawal_reaches_every_prompt.py`. A `ts -> row` map is `nora.domain.quote_window.first_by_ts` and nothing else (`tests/architecture/test_one_quote_resolver.py`).
8. **Classify a module that runs a prompt it does not build.** A MECHANISM, RUNNER or EXEMPT entry with a reason in the enforcer; a RUNNER names every builder, and each must itself be declared. The test re-checks the entry (the module exists, still calls a model, a RUNNER's builders exist and an `imports` runner imports one) but cannot read what the module does with the prompt it is handed, so the entry is reviewed in the PR that adds it, and a module that also writes prompt text of its own is not a RUNNER.
9. **Capture goldens before you change an existing occasion.** Render its CURRENT output over realistic, generated fixtures into golden tests first, commit them against the old code, then refactor and show they still pass; a step declared byte-identical that is not is a defect. If byte-identity is impossible, stop and say what differs, because that is a prompt change and wants the operator's eval. No test enforces this: it is review (`tests/unit/test_*_goldens.py` are the examples).
10. **Prove it by reverting.** Replace one `assemble` call with a hand join and the enforcer goes red; keep that as a row in a `scripts/mutations/` table (`context-assembly-6-close.json` shows the shape) and run `make mutate`.

**What the net cannot see**, so review covers it: the list in §4 (a hand-built text inside a runner, a mechanism or an exempt module; a model door it does not know; a call reached only through a helper; a `_BLOCKS` walked over a list that does not come from it; anything outside `nora/`). There is no debt list to record such a gap in: fix it, or give it a purpose-built architecture test like `test_framing_is_one_typed_place.py`.

Discord's and Instagram's events name no deleter (`sender_id == ""`), are authenticated by the platform and are honoured as it reports them; a moderator's removal is a legitimate withdrawal from the room.
  - **A delete whose target is not on record** (it overtook its message, because Discord dispatches events as separate tasks and a photo is recorded after its custody fetch; it arrived after a restart or long before its message; or its target lookup failed) is kept in `orphan_delete` (migration `0088_orphan_delete`, amended before it shipped; a NEW table, `messages` is untouched; a `HISTORY_TABLES` table with the row-history trigger, so each row leaves an insert and a delete version of platform ids only, with no runtime pruning of `row_history`). It is written FIRST, in its own transaction, before the second look at the target, so a failed lookup loses nothing; it is checked right after a message is audited under ONE key-and-authorship rule (`orphan_names_message`, shared by the pipeline, the fake and the sweep: same platform and room, a non-empty platform handle or Signal's sent-timestamp, and the author on Signal and WhatsApp) and applied DIRECTLY to the row just audited (the delete's own record, which carries the deleter's id forms, then the hide and the cascade), and only THEN discarded, so a crash in between leaves the row for the sweep (at-least-once, idempotent). **A refused delete leaves no `message_delete` record, but a stranger's delete for a target not yet stored stays in `orphan_delete`** (authorship can only be checked once a target exists): it is never applied to a message that is not its author's, and the table is bounded: one row per delivery (unique key), an AGE WINDOW, a 3-day TTL and a SOFT cap per scope enforced by EVICTION, never by refusal. **Age window: an ASSUMPTION about the ingest paths, not a proof.** A delete whose target is not on record and is older than 30 minutes when it arrives (`ORPHAN_RACE_WINDOW_MS`; exactly 30:00 is held, 30:00.001 is stale) is DROPPED, not held, and counted `orphan_stale_target`. The age is read off a Discord snowflake (`(id >> 22) + epoch`) or a Signal sent-timestamp (the event's time minus it); WhatsApp and Instagram handles carry no time and are always held; a lookup that FAILED is never taken for «not there». It measures how long the sender waited before deleting, while the race a held delete exists for is whether the delete reaches Nora before its message: the window assumes a message reaches Nora within seconds of being sent (a custody fetch, a task scheduled late), that a restart replays nothing, that Signal is strictly serial and that there is no history backfill. Two paths are known to break it and neither is verified: a Discord gateway RESUME replaying an outage longer than the window (how long Discord keeps a session resumable is unconfirmed) and a linked Signal device with a skewed clock. There the delete is dropped, the message arrives later and **stays visible and fed to memory: the leak direction.** `nora withdrawal reconcile-deletes` cannot recover it (nothing is on record); the sender deleting it again can, and so can `nora person forget`. **Caps:** a NAMED deleter at most 40 (counted across the platform), an UNNAMED one (Discord and Instagram deletes name nobody, `deleter_id == ""`) at most 500 per room (never one shared bucket for the platform), a room at most 1000, everything at most 10000. **Eviction order, per scope:** the deleter's own oldest rows first (true of THIS scope only), then the room's, where the row that goes is the oldest of the deleter holding the MOST rows there (the unnamed bucket counts as one deleter; a deleter whose rows are all claimed by other writers is passed over for the NEXT-heaviest, never for the room's oldest row), then the overall oldest. Rows are claimed `FOR UPDATE SKIP LOCKED`, so concurrent writers never wait on each other's rows (a plain delete deadlocked across rooms: the reviewer saw about 525 in a probe), and the touch stage makes four attempts (three retries) with random pauses and then counts `orphan_lost`. **A new held delete lands unless a concurrent writer deadlocks and all four attempts fail, and it can be evicted by a flood at the room or overall scope or, on Discord and Instagram, by 500 unnamed deletes of recent-looking ids in the same room while its message is on the way.** **Residual risk, a leak-direction one:** eviction, a lost write, a stale-target skip and the TTL are not a safe direction: the delete's message, if it then arrives, stays visible and is fed to memory. Evicting a lone row at the room scope is an ARITHMETIC matter, not a mechanism: the per-deleter cap holds across the platform, so five colluding WhatsApp members hold at most 200 rows and never reach the room cap; the room is reached only by more than 25 flooding members, and then heaviest-first spares a lone row unless every deleter holds a single one. On Discord and Instagram the unnamed cap of 500 binds before the room scope, so the unnamed flood is the one that can evict, and heaviest-first only matters for WhatsApp and Signal rooms. None of this was loud: a loss is a counter and one log line with no ids, so `OrphanDeleteLost` (any `orphan_lost` in 1h) and `OrphanDeleteEvicted` (more than 50 `orphan_evicted` in 1h, a pick) alert on them, and both counters are created at zero at start (`docs/observability.md`). The in-memory hold #711 first shipped is REMOVED: the row covers everything it covered. The match reads a handle index and a sent-timestamp index through the room (a few indexed lookups per message audited, not a table scan; measured with a plan on 30k rows). The sweep resolves held deletes against stored messages in set-based batches of 300 (one join per batch, the rule in Python), bounded whatever the table holds, and purges what is past the TTL (`orphan_expired`).
  - **One central guard, for the window between a message's audit write and the stages that read it.** Right before an audited message is handed to ANY downstream stage (memory feed, stimulus, Standing and note stages, the gate) its row is read again by primary key and a hidden row stops the pipeline (`IngestPipeline._guard`, outcome `withdrawn`). A read that fails is asked once more; a single transient failure costs nothing. A KNOWN held delete that could not be applied stops it (`withdrawal_pending`, `apply_failed`, the row left for the sweep); a read that fails TWICE stops it deliberately with its own outcome (`guard_read_failed`: no delete is known, the database is failing, and a message fed on a guess is the worse way to be wrong). It closes that window and no other: a delete that arrives after the read is the ordinary after-the-fact case, hides the row for every later read, and what was already fed or answered stays so (Honcho, A2 below); no reply path re-checks the flag before sending, a few lines against the send path but one that can misfire on a message hidden for another reason, not done. The edit path applies a held delete that names the original or THIS edit (Signal names an edit by its own timestamp) and asks the same question about the original. Cost: three statements per message (the insert, the held-delete match, the hidden read), one more than before this change.
  - **One lock order.** A writer that cites a message takes `FOR SHARE` on the cited messages, SORTED by id, at the START of its transaction, before it locks its own note or event row (`citation.lock_cited_messages`: note create and revise, event create and update); the curator's batch (`SqlNoteStore.propose`, one transaction) takes it ONCE over the whole batch's cited ids before its first write, because a lock per write meant message locks taken after an earlier note's row was held. The delete hides the message first and cascades after. The reverse order deadlocked and ended the delete `cascade_failed` (its retry and the sweep repair it). `person forget`'s multi-row hide locks its rows in id order first. The lock removed from note create or event create is an equivalent mutant: a row that does not exist yet cannot be seen by the cascade.

# Discord Music — Player State & Queue Persistence

## Two different lifetimes, deliberately not stored the same way

- **Now-playing / playback position** — in-memory only, on a per-guild
  `MusicPlayer` object (one instance per `guild_id`, held in a manager
  dict alongside the voice connection). Lost on a process restart AND on a
  Gateway reconnect (`02-control-surface.md`). Accepted: you cannot resume
  mid-audio-frame without reconnecting to the exact channel and re-seeking
  into a stream that may no longer resolve the same way, and a restart is a
  deliberate deploy event, not a random mid-song crash.
- **The upcoming queue** (what's queued next) — persisted, because losing
  someone's 15 queued songs on every deploy is a real, avoidable annoyance
  that costs almost nothing to avoid, unlike resuming playback position.

## Why Postgres, not Valkey, for the queue

Valkey was the first instinct — it's already running in this stack
(`docker-compose.yml`'s `valkey` service) — and it was wrong, for a
verified reason: **`grep -rn "valkey\|redis" nora/` returns nothing** (only
unrelated hits). Valkey is `drop`'s own dependency
(`VALKEY_URL=redis://valkey:6379/0`, `deploy/drop/`), not Nora's — Nora's
process has zero Redis/Valkey client today. Reusing it would mean adding a
brand-new client dependency to Nora's own process for the first time, not
"reusing infrastructure that's already there for free."

Once that advantage evaporates, Postgres wins outright:

- **Zero new dependency** — Nora already has a Postgres pool
  (`nora/infra/sql/`); a `music_queue` table is one more row in an existing
  migration chain.
- **Consistent with A9** ("Postgres is the record") and with how every other
  piece of restart-surviving mutable state in this codebase already lives
  (reminders, facts, notes) — if it needs to survive a restart, it's a
  Postgres row, full stop. A second "needs to survive a restart" store
  existing alongside Postgres, for no reason but that Valkey happens to run
  in the compose file for a different service, would be the kind of
  decision `design/18-media-custody.md` §3 already warned against: sizing
  infrastructure against zero evidence of need.
- **Scale kills the case for a cache tier.** A personal Discord server's
  queue is tens of rows, mutated a handful of times per session — Valkey's
  actual selling points (high write throughput, native TTL) buy nothing at
  that volume. No TTL is needed either: a row is `DELETE`d when its track
  finishes, is skipped, or the queue is cleared — never expired.

## Schema shape

One table, modeled directly on the hand-written-migration pattern
`nora/infra/sql/migrations/versions/0004_reminders.py` already establishes
(a `CHECK` constraint that `alembic check`/`compare_metadata` cannot see, so
the migration is hand-written rather than autogenerated — `CLAUDE.md`'s own
note on this):

- `guild_id`, `position` (ordering within the guild's queue)
- `source` (which `TrackSource` resolved it — `01-playback-and-source.md`),
  `url`, `title`
- `added_by_person_id`, `added_at`

No `expires_at`. No foreign key to a "session" concept — the queue table
*is* the session's durable half; there is nothing else for a row to point
at. Migration number is the next one after the current single head
(`0027_fact_candidate_provenance` at the time this bundle was drafted —
**re-verify with `uv run alembic heads` at implementation time**, per
`CLAUDE.md`'s standing warning that a parallel session may have claimed the
next number first).

## Disconnect behavior — deterministic, not agent-decided

Two independent timers/events on the manager, neither an LLM decision:

1. **Voice channel empties of humans** → leave immediately.
2. **Queue empties and nothing is playing** → leave after a configurable
   idle timeout (5 minutes as a starting default), the same way this
   codebase already holds timeouts in `config.toml` rather than hardcoding
   them.

## Connect trigger

On the first successful `play` (via slash command; `02-control-surface.md`)
for a guild with no active voice connection: join the invoking user's
current voice channel. No separate "connect" step a user has to remember to
run first.

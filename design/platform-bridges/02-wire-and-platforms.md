# Event and transport boundary — proposed

Every interface, field and route below is **proposed**, not an existing implementation.

## Inbound v1

One stream per platform/account, named using an opaque account key; one group `nora-v1`, created at `0-0` before consumption. A single bridge capture sequencer per account orders callbacks; stream order is receipt order, not a claim about globally ordered source clocks. Per-conversation DB ingestion follows this order; different conversations can run concurrently. The app stream reader durably registers entries in order before parallel execution, so two consumers cannot register a later event first. Only the elected reader (Postgres advisory lock per stream) does XREADGROUP/XAUTOCLAIM; work executors use DB claims. This is deliberately one reader, not partition infrastructure.

Each XADD has a JSON envelope with:

- `version=1`, `event_id` (opaque stable keyed HMAC of canonical source key), `platform`, opaque `account_key`, `kind` (message/edit/delete/reaction/summons), `source_key` private to payload, `source_time_ms`, `received_at_ms`, `enqueued_at_ms`, `time_quality` (source/arrival), conversation target and sender identity.
- `message`: the serialized NormalizedMessage fields, including typed edit/touch, structural mentions, original quote facts and raw provenance; app rehydrates, never re-parses. Keep source timing separate from Redis ID and wall-clock receipt. Missing required identity/version is a retained malformed event, not a guessed message.
- Opaque `quote_ref`/`reaction_ref` tagged with platform and account; Signal author+timestamp, Discord snowflake, WA stanza key and Instagram message handle remain different types. Both typed domain facts and transport reference survive, without deriving one platform's handle from another's.
- Attachment handles: bridge-owned immutable object key, hash/size/type, authorized fetch route and expiry/pin state; never a bare app-local path or upstream expiring URL as the durable reference.
- `traceparent`/validated `tracestate` from the producer operation; no baggage. Event identity and trace identity are different. A missing/invalid trace context changes diagnostics only.

Source keys include platform, account, conversation, event kind and upstream message/revision/transition identity. Use a dedicated named private correlation key resolved through the canonical secret contract; do not expose guessable unsalted hashes of private IDs. Key rotation preserves existing event IDs/mappings and starts a new key version for new input; replay resolves source mappings against every still-live key version before assigning a new ID. Retain old keys/mappings for the supported replay horizon; only current-version aliases are newly written, pointing to the original event/stream identity when found. Postgres uniqueness uses the canonical, key-version-independent source tuple, never its rotating digest. Signal messages use sender+sent timestamp, edits target+edit timestamp; Discord messages use snowflake and edits edited_at; WA/IG use upstream message and revision identifiers when present. Reactions include target, reactor, emoji, removal and transition identity; add/remove/add must produce three events. A body hash alone cannot distinguish that sequence.

When no upstream transition identifier exists, bridge capture persists a per-target/reactor transition sequence and last observed state before publication. Repeated same-state callbacks are duplicates; an observed state change increments the sequence. Reconnect replay without a source revision that can distinguish an old transition from a new one is **ambiguous**, retained for diagnosis without fabricating a new transition. This is an explicit upstream limit and a per-platform fixture prerequisite, not permission to drop valid events. Original raw metadata needed for this determination stays private in the queue/store, never telemetry.

Use one Redis Lua operation: look up source-key digest; if present return original stream ID/event ID; otherwise XADD then store digest->ID. No expiry while queued/pending/retained or within supported upstream replay history. Serialize operations with the account sequencer; producer retries reuse the original envelope and producer context. Redis script errors never authorize a receipt. Avoid Lua writes before XADD that could leave a marker without an entry on storage/type failure; validate key types first and use a dedicated namespace. App DB uniqueness remains the final dedupe after Redis recovery/pruning.

A small fsynced append journal in each bridge's private durable volume holds captured normalized events until Redis confirms enqueue; retry head first. Before enabling upstream receiving, verify the journal append-and-fsync path; a failed preflight refuses receive on every restart. Append record+checksum, fsync before declaring captured, recover/truncate only an incomplete tail, never overwrite retained evidence. Persist source-key/transition mapping and enqueue confirmation in that same journal. It is a producer retry spool, not a DB publication outbox. Failure to durably capture (journal disk-full/write failure, lost capture subscription or failed sequencer) halts upstream receiving as well as receipts; health alone is insufficient. For Signal, stop the signal-cli child and exit the wrapper rather than leaving an unhealthy daemon draining messages. Redis unavailability alone may continue capture only while the healthy journal durably retains every event; stop upstream receiving when that capacity is exhausted. Never drop oldest. The upstream-to-capture gap remains possible, especially signal-cli SSE, because upstream provides no transactional enqueue handshake. App-only releases do not touch that receiver. Bridge or host outage cannot honestly promise all upstream deliveries survive.

## Admission and receipt

Bridge receives a validated, read-only transport admission projection generated by the **same app policy/identity code**, refreshed independently of the app process from canonical local files. It contains only enabled account/room/DM-address scopes, self aliases, deterministic mention/reply trigger facts, reaction flag and revision. Concretely the file carries `revision`, `generated_ms`, `enabled`, `account_key`, `rooms`, `dm_allowed_senders`, `self_aliases`, `deterministic_triggers`, `receipt_emoji`, `room_receipt_senders` and `music_channels` — `room_receipt_senders` maps each admitted room to its grant as a sender-id list, or the literal `["*"]` only for a `persons = "*"` policy wildcard; a room absent from the map is a receipt deny. Do not mount credentials or all identity information for this purpose. The projection helper can run as part of bridge supervision, without models. Startup without a valid projection refuses content capture/receipts; invalid reload retains last good projection under existing reload semantics, with stale health. Bridge checks known denied/unconfigured rooms before spooling bodies or media. No model gate, context lookup or business engagement judgement runs there.

Allowed ambient rooms may be persisted for the app's existing ingestion even if not eligible for a receipt. Send a queued receipt only for enabled reactions and deterministically eligible addressed events from admitted senders, after successful Redis enqueue, using a stable receipt action ID. After bridge restart, enqueue confirmation re-derives a pending receipt step from the original event ID and receipt phase; the action store reuses a confirmed result, attempts only definitely unstarted work and retains a started/uncertain result without blind replay. A later progress/terminal phase suppresses an older queued receipt. Unknown/model-decided participation eligibility gets no receipt. Explicitly denied senders get no receipt; retain only content current room absorption rules permit, matching existing audit-vs-answer distinction. No raw content of denied rooms is journaled. On backlog consumption and immediately before effects, app rechecks current policy and identity; revocation cancels outstanding work and releases media pins. Receipts reflect admission at enqueue time, never a continuing grant.

## One synchronous wire API

Shared client implements PlatformAdapter unchanged at its call surface; durable action context is injected through collaborators when constructing the turn adapter. Proposed authenticated routes:

| Route | Request / response |
|---|---|
| POST /v1/actions | version, action_id, typed durable owner (work/event-receipt/OTP-challenge/live-invocation) and generation for work-bound actions, platform-qualified target, operation send/react, text/decorations, quote/reaction reference, attachment handles; outcome below |
| GET /v1/actions/{action_id} | Stored outcome or explicit absent/in_progress/uncertain; absent is only retry permission if no prior intent/effect evidence exists |
| GET /v1/self | Real identity/aliases/capabilities, no placeholder identity |
| POST /v1/reads | operation roster/channels/member_presence/voice_presence, scoped target/member IDs; ok/nothing_found/unavailable with observation time |
| PUT /v1/attachments/{opaque_key} | Bounded bytes, content hash/type, pin tied to work/action; identical bytes/key idempotent, conflicting hash refused |
| GET /v1/attachments/{opaque_key} | Authenticated bounded bytes; not arbitrary filesystem or URL access |

Every action response carries `action_id`, `state` (`prepared|started|confirmed|rejected|uncertain`), `outcome`, `platform_ref`, sanitized `error` and `message_id` — the pending-outbound audit row the action bound at start, so a client whose POST answer was lost reconciles through `GET /v1/actions/{action_id}` to ITS `messages.id` instead of resending. The durable owner is `{kind, id, generation}` — `generation` is required for `kind=work` and the bridge verifies it against `bridge_work.generation` before effects (mismatch = fenced rejection), so a reclaimed lane cannot re-execute under a stale claim.

Send returns `confirmed` with platform reference/time, `rejected` with retryability/retry_after when definitely not submitted, `unsupported`, or `uncertain` with retained attempt evidence. A 202/in-progress is not confirmed. Map confirmed to SendResult.ok; add an explicit outcome/reference to SendResult (and ambiguous delivery status if required), preserving existing callers and checks. Retryable must be false for uncertain. Decoration-only unsupported features degrade to plain text according to existing port rules; unsupported send/media/react does not fake success. Reaction result retains unsupported/failure distinctions. Validate target platform matches endpoint/account and reject mismatches before effects.

Reuse `nora/infra/service_auth.py`'s bearer pattern on all account/event/action/blob/read routes, with no published ports. Signal raw RPC binds loopback inside its wrapper container. Redis uses private network plus ACL users constrained to producer/consumer/inspection commands and namespaces; named credentials through private secret.toml/native environment projection, never template values. This is a trusted internal deployment boundary; no public multi-tenant API is proposed.

Deployed wiring envs (bridges read these names; secret values never enter templates): `NORA_REDIS_URL` (producer-scoped URL), `NORA_BRIDGE_API_TOKEN` (shared Bearer; `NORA_BRIDGE_TOKEN` is the deployed fallback for older bridges — API_TOKEN wins when both exist), `NORA_BRIDGE_CORRELATION_KEY` (hex HMAC key) + `NORA_BRIDGE_CORRELATION_KEY_VERSION`, `NORA_BRIDGE_ACCOUNT_KEY` (required per bridge — the opaque stream leg, never derived from a platform id), `NORA_BRIDGE_JOURNAL`, `NORA_BRIDGE_PROJECTION_DIR`, `NORA_BRIDGE_ATTACH_DIR` (attachment custody; created at boot where set), `NORA_BRIDGE_PORT`, and `DATABASE_URL` for the action store. `DATABASE_URL` arrives as the app's SQLAlchemy dialect string (`postgresql+asyncpg://…`); consumers on other runtimes strip the `+driver` qualifier before their driver parses it. Voice/music configuration is NOT an env surface: the Discord bridge mounts the deployment's `config.toml` read-only and reads `[platforms.discord] mode`, `[speech.tts] sidecars` and `[music]` through the same `config.load(require_secrets=False)` the app uses — one config truth, and the graph exists only where `mode = "bridge"` makes the app relinquish it.

Media stays in a bridge durable spool through queue wait and app replacement. App's existing custody stage copies authenticated bytes into its existing content-addressed blob store before audit; hash/size validation is mandatory. Upload outbound bytes to bridge custody before send, pin until result is settled. Release ingress pins only after DB custody/retained failure disposition and replay-safe retention; never tie deletion to HTTP connection close. Preserve existing configured media degradation, but record explicit unavailable custody instead of pretending no media arrived.

## Platform ownership

**signal-bridge:** new wrapper supervises the unmodified signal-cli executable, subscribes continuously to loopback SSE, owns normalization/spool/Redis and common send/react/read routes. Preserve signed 0.14.7 distribution and Java25 unless separately changed. Preserve `./state/signal-cli:/data/signal-cli`, XDG_DATA_HOME=/data, uid/gid 1000 and private permissions exactly. Add a separate spool volume, never put keys in app data. Start the CLI with `--receive-mode on-start` only after the journal append-and-fsync preflight succeeds; a child/capture failure stops signal-cli and exits the wrapper. An unhealthy-only state is allowed only when receiving is already halted or events remain durably captured; it never substitutes for stopping a receiver with broken capture. No relink/re-register/unlink/reset or account store relocation. Protect wrapper API; raw daemon cannot be reached from other containers.

**discord-bridge:** move discord.Client, Gateway listener/intents, command tree, member/channel/presence reads and transport sends into this independent Python process. Reuse discord.py; retain heartbeat/resume behavior, raw edits/deletes/reactions and per-channel sequencing. Discord documents [Gateway sessions/resume and intents](https://docs.discord.com/developers/events/gateway); invalid sessions and history catchup do not establish immediate reactions while the app is down.

Move MusicPlayerManager, its existing SQL queue/session stores, deterministic slash-command handlers, liveness watch and notification routing alongside that client. The bridge is the sole music manager, not a duplicate in Nora. App music tool port forwards authenticated deterministic commands to it; bridge verifies the supplied policy-scoped guild/requester and reads actual member voice state. App owns model/tool authorization and policy projection owns slash admission. Keep existing external audio controllers, HttpVoiceSession and VoiceControllerHub protocol: controller voice connection/playout remains there. Bridge owns hub adoption/reconciliation and controller event consumer; app voice sends forward bounded speech bytes through the bridge to the same generation. Member/voice/presence reads become RPC returning unavailable if Gateway cache is not ready, never fake offline. Callback routing and boot adoption run independently of app releases. Existing configured music/voice endpoints must migrate together; no second controller or bot session.

**whatsapp-bridge:** keep Baileys session and JID/phone/LID mappings; replace bounded SSE buffer correctness with journal+Streams and move pure normalization from app parser to handler parity vectors. Media bytes are held before expiring platform download references are lost. Common actions translate into existing send/react operations.

**instagram-bridge:** extend existing Go layering with normalized stream publisher/common action facade over existing use cases; retain authenticated resource/social/profile/search routes and degraded-session health. Edits, reactions, unsends and summons keep distinct kinds. Existing resource paths remain for non-message callers; app delivery uses the common wire. No second social gateway and no browser login change.

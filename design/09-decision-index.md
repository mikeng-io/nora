# Decision Index

Decisions live inside long documents under eight identifier namespaces with no
index (`D*`, `A*`, `R-*`, `S*`, `C.*`, `E.*`, `M*`, `DEC-*`), and production
modules used to cite section numbers of a spec since superseded. Rules are
versionless; section numbers are not. This file is the index for the four
namespaces that carry live, enforced decisions: `D*` (topology), `A*` (audit
amendments), `R-*` (guardrail rules), `DEC-*` (architecture). `S*`, `C.*`,
`E.*`, `M*` are structural/procedural section labels inside
`docs/superpowers/specs/2026-08-03-nora-strands-spec.md`, not decisions in
their own right, and are not indexed here.

See `ARCHITECTURE.md` for the map this index supports, and each identifier's
defining document for the full rationale — this file is deliberately terse.

| R-20 | **Quoted text shown to the model is the resolved parent ROW's text, or nothing** (`design/11-recall-and-threading.md` §2.4). `build_tag_message` used to render `dataMessage.quote`'s own `text`, attributed to a named author, inside `<tag_message>` — and that text arrives in the QUOTING sender's envelope, verified against nothing, so Alice could construct a quote asserting Bob said anything at all and Nora would relay it back into the room as Bob's words. | R-21 | **A room-scoped tool resolves names only within the conversation it was bound to, and "not in this room" is indistinguishable from "does not exist".** `group_members`, `lookup_person` and `recall` (`nora.agent.tools`) all resolve inside `nora.agent.room.RoomView.people` — the platform's own membership list for THIS conversation, intersected with `identity.toml` — never against `Persons.index`, which is Nora's address book across every room she is in. The mechanism is **resolve-within-scope, never resolve-then-filter**: the name/alias index `find` runs against is BUILT from this room's members, so a person who is elsewhere is not found-and-rejected, they are absent from the index. Resolve-then-filter would leak membership — and the existence of people in other rooms — through the difference between "no such person" and "not here", which is the 2026-08-06 roster leak in a slower spelling: asked who was in the group Nora listed five people who had never been members, and R-18 saw nothing to block because the leak carried only names (design/12 §3). **By the time text exists the disclosure is already authorised**, so this is enforced at ASSEMBLY. Two consequences worth stating: alias matching is safe HERE while design/10 §1.3 still forbids an alias ever resolving a SENDER (the target set is bounded before any alias is consulted, and `nora.persons.Persons.index` is untouched — `tests/test_persons.py::test_an_alias_never_resolves_a_sender` still holds); and none of the three accepts or returns a platform identifier, so they cannot confirm that an id belongs to a member, and nothing they hand the model is something R-18 would have to block on the way out. | `test_not_being_here_is_indistinguishable_from_not_existing` (`tests/test_room_tools.py`); `tests/unit/test_agent_room.py::test_a_person_in_identity_toml_but_not_in_this_room_is_not_found` |
| R-22 | **A tool that could not answer says so in its RETURN VALUE, and "asked and nothing known" is never the same value as "could not ask".** An empty result that reads as "nobody is here" is a confident lie the group acts on; a raised exception kills the turn. So each of the three room-scoped tools returns a `status` — `ok` / `not_found` / `ambiguous` / `nothing_known` / `unavailable` — and every one is counted (`nora_room_lookups_total{tool,status}`, plus `nora_recall_total{status}` for the Honcho call specifically). **The counter has to live at the call site**, because neither transport can express the distinction: signal-cli returning `[]` for a group Nora is demonstrably in is a real observed state (stale group state on a linked device — CLAUDE.md constraint 3), and Honcho's `representation` answers **200 with an empty string** for a peer it has never heard of rather than 404. This is `peer_card`'s failure written down: it returned `[]` both when Honcho was down and when it knew nothing, so a dead endpoint answered "I know nothing" on every call for the entire life of the deployment and "a missing card is normal" was a true sentence that made it invisible. Consequences: an unreadable roster makes `group_members` `unavailable` and never an empty list; a lookup MISS while the roster is unreadable is `unavailable`, not `not_found` (the scope narrows to the tagger, which is a strict subset of the room and so cannot say what the room does not contain); and a `MemoryStore` that raises lands on `unavailable`, never on empty. | `test_nothing_known_is_distinguishable_from_could_not_ask` (`tests/test_room_tools.py`); `tests/test_honcho_representation.py::test_an_unknown_peer_is_reachable_and_empty_never_unreachable`; `tests/contract/test_roster_source_contract.py` |
| R-23 | **A turn that ran out of budget is never reported as a turn that chose not to speak.** Strands ends a turn that hits one of R-8's caps by yielding an `EventLoopStopEvent` with `stop_reason="limit_total_tokens"` (or `limit_turns` / `limit_output_tokens`) and RETURNING — measured end to end against 1.50.2: no exception, no log line, no warning anywhere in the SDK. `nora/` never read `stop_reason` at all (zero hits), and `LiveAgentRunner.invoke` awaited `factory.invoke(...)` and DISCARDED the `AgentResult` it returned. So `invoke.run` reported `ok=True`, the pipeline found nothing delivered, ⚠️ fired and `nora_silent_failures_total{reason="no_send_call"}` incremented — **byte-identical to the model simply choosing not to call `send_reply`.** The single most likely cause of a silent turn was indistinguishable from the most benign one, and the budget was crossed during model call FIVE of an alleged eight (see R-24), so this was not a corner case. The `AgentResult` is now kept, `stop_reason` is threaded `LiveAgentRunner` → `invoke.run` → `deliver.check_outcome`, every completed invocation is counted `nora_llm_stop_reason_total{reason}` (including `end_turn` — a series that only ever carries `limit_*` cannot say what FRACTION of turns are cut off), and a silent turn whose loop ended on a cap is labelled with that cap instead of `no_send_call`. `check_outcome`'s `stop_reason` has **no default**, so a new call site cannot quietly restore the old behaviour. Only the three BUDGET reasons are relabelled: `end_turn`/`max_tokens` with no reply is still a model that chose not to speak, and swallowing that would trade one blind spot for another. This matters more than R-24's numbers — raising a cap without this just moves the cliff, and it is the difference between finding the next one in an afternoon and it running 61 days like the `--receive-mode` bug. | `test_a_budget_stop_is_distinguishable_from_a_silent_model` (`tests/integration/test_turn_budget_is_legible.py`); `tests/unit/test_engagement_deliver.py::test_a_turn_cut_off_by_a_budget_cap_is_not_labelled_no_send_call`, `::test_an_ordinary_stop_reason_still_counts_no_send_call`, `::test_check_outcome_cannot_be_called_without_a_stop_reason`; `tests/unit/test_engagement_invoke.py::test_the_stop_reason_is_counted_on_every_completed_invocation` |
| R-24 | **No single model call, and no single tool result, may spend the whole turn's budget.** Three violations, all measured 2026-08-06, all previously invisible because a budget that is too small does not fail loudly — it just ends the turn early (which, before R-23, read as the model declining to answer). (1) `build_limits` set `"output_tokens": max_tokens`, making the WHOLE LOOP's output budget equal to ONE call's ceiling; measured single calls emitted 3,993 / 3,987 / 3,974 completion tokens against `max_tokens = 4000`, i.e. 99.8% of it. `output_tokens` is now its own `[llm.limits]` field (12,000 = 6x the per-call ceiling) and `build_limits` has no `max_tokens` parameter left to pass. (2) Real per-call INPUT is 4,952 tokens, paid again on every call, and a measured 6-call turn totalled 32,426-36,748 — so `total_tokens = 24000` was crossed during call FIVE and `turns = 8` was unreachable dead config. `total_tokens = 64000` gives ~2x headroom and lets `turns` bind first, which is the cap an operator can reason about because a turn is a round trip and a token is not. `max_tokens` drops 4000 → 2000: the largest LEGITIMATE completion measured was 371 tokens, so that is 5.4x headroom, and it no longer doubles as the loop budget. (3) `read_buffer`'s `limit` is the one number in `nora.agent.tools` the MODEL invents on every call and nothing downstream bounds it, so the clamp is the only thing between it and the turn: `read_buffer(200)` cost 6,592 tokens (vs `read_buffer(40)` 1,368, `recall` 151, `lookup_person` 112) and is re-charged on every later call of the loop, so at `budget: 2` two calls were 13,184. Clamped 200 → 60, default 40 → 25. The ceiling is a LITERAL in the docstring rather than an interpolation because the docstring IS the model-facing schema — an f-string there would leave `__doc__` empty and Strands would derive no description at all — so a test pins the literal to `READ_BUFFER_MAX` instead. Asserted against **both** config files: `config.toml` is what this deployment runs and `config.example.toml` is what a fresh install gets and what `tests/test_config.py` loads. | `test_no_single_call_can_spend_the_whole_turn_budget` (`tests/test_turn_budget.py`, parametrised over both config files); `::test_both_config_files_declare_the_same_budget`; `::test_the_read_buffer_clamp_is_the_only_bound_on_a_model_supplied_size`; `::test_the_model_is_told_the_same_ceiling_the_clamp_enforces`; `tests/test_factory.py::test_build_limits_takes_the_loop_budget_and_never_the_per_call_ceiling`; `tests/test_tools.py::test_read_buffer_clamps_the_top_end_to_the_declared_ceiling` |
| R-27 | **An empty answer from one operator is never reported as "there is no such thing" until the thing has been shown not to exist.** `transit`'s three states are `ok` / `nothing_found` / `unavailable`, and the split inside `nothing_found` is the rule: a route some operator's CATALOGUE lists and a route no catalogue lists get different sentences, and a catalogue that could not be read makes the answer `unavailable` rather than a claim about the route. Measured 2026-08-06, and this is why it is a correctness requirement rather than a nicety: `getSchedule` answers `200` with `status: "0"`, `caseNumber: 1` and `busStop: []` for `ZZZ999`, **and returned the byte-identical envelope for eleven real published MTR routes at 23:15** (K12, K14, K51A, K52A, K52P, K53S, K58, K65A, K74, K75S, K76S) simply because they had stopped for the night. Nothing in an ETA response separates the two, and the four fields that look as though they might — `caseNumber`, `routeStatus`, `routeColour`, `routeStatusRemarkTitle` — are every one of them marked *Deprecated* in MTR's own Data Dictionary v1.19. Without the catalogue check 「而家冇車」 is said about a bus that has never existed, confidently, in a sentence indistinguishable from a true one. See DEC-40. | `test_an_unknown_route_is_never_reported_as_no_service` |
| R-27b | ...and the same rule on the PLACE axis: «that place exists but this route does not go there» (`not_on_route`) is a useful, checkable sentence — 「K73 唔經天水圍站」 — and is never collapsed into «no stop by that name» (`not_found`), which only a LOADED stop dataset entitles anybody to say; stop data that could not be read makes the place answer `unavailable`, never a claim either way.

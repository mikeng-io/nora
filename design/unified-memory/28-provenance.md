# 28 · Provenance, referenced to W3C PROV

Operator, 2026-10-29: reference PROV's architecture and the way it is used,
without adopting it wholesale or its RDF topology. The graph stays plain
Postgres ([27](27-the-memory-is-a-graph.md) §16); PROV is the vocabulary we
check our provenance against and borrow names from.

Sources: [PROV-OVERVIEW](https://www.w3.org/TR/prov-overview/),
[PROV-DM](https://www.w3.org/TR/prov-dm/) (Recommendation, 2013-04-30),
[PROV-O](https://www.w3.org/TR/prov-o/),
[PROV-CONSTRAINTS](https://www.w3.org/TR/prov-constraints/).

## 1. PROV's architecture, and ours

PROV is not one document. It is **one conceptual model (PROV-DM)**, with
**separate encodings** (PROV-O for RDF, PROV-N for people, PROV-XML), and
**separate validity rules (PROV-CONSTRAINTS)** that say which provenance
is valid, written for whoever builds a validator. The model never depends on
an encoding, and validity is a separate artifact, never implied by the
schema.

The graph already has that split, and this node makes it deliberate:

| PROV | role | ours | owner |
|---|---|---|---|
| PROV-DM | the model | the `entity` / `relation` / `relation_evidence` stores and their domain types | `nora/domain/memory_graph.py` |
| PROV-N, PROV-O, PROV-XML | encodings | the labelled preview rows a model reads, Views, receipts | the renderers (`comprehend_render`, Views) |
| PROV-CONSTRAINTS | validity | admission: vocabulary, ends, layer, evidence, span, scope | `validate_relation`, `memory_admission` |

**One rule follows:** a renderer never decides validity, and admission never
formats. A new encoding (an export, a PROV-O dump for an audit) is one more
renderer over the same rows, with no change to the model.

## 2. The core: entity, activity, agent

PROV-DM's core is three types and the relations between them: an
**entity** is generated by an **activity**, which used other entities and is
associated with an **agent**, to which the entity is attributed.

| PROV | means | ours |
|---|---|---|
| Entity | a thing whose origin is described | a Record item (message, page, reading), a relation, a Notebook entry |
| Activity | what produced it, over time | a `cognition_session` row (step 1 or 2), a code projector's write, a Rollup tick |
| Agent | who answers for it | a person, Nora, the model behind the session, code |
| wasGeneratedBy | entity → activity | `relation.written_by` (adaptor and session id) |
| used | activity → entity | `cognition_session.from/through_stimulus_id`, and the `shown_sources` receipt (§6) |
| wasAssociatedWith | activity → agent | `cognition_session.model_id`, `model_route` |
| wasAttributedTo | entity → agent | `authored_by`; a reading's speech act (stated / said by another) |
| actedOnBehalfOf | agent → agent | the model acts for Nora; an `operator` revision source acts for the operator |

**Name clash, on purpose kept.** Our `entity` table holds the things the
world is made of (a person, a place, a topic), which is what PROV entities
are *about*, not PROV entities. Read "entity" in this repo as the graph's
`entity` unless a sentence says PROV.

## 3. Qualification: a binary edge, and a side record when it needs more

PROV-DM keeps every core relation binary and **qualifies** one only when it
needs a role, a time, a plan or attributes, as an n-ary record of the
influence (PROV-O's `qualifiedDerivation`, `qualifiedUsage`). The binary
form stays walkable; the qualified form carries the detail.

The graph does the same and should keep doing it:

- `relation` is the binary edge every walk follows (WALK_SQL).
- `relation_evidence` is its qualified derivation: the source, the `role`
  (supports / contradicts), and the `span`. A span is PROV's
  **Quotation**: the part repeated verbatim, checked against its source.
- A new detail about an edge goes into a side record, never into a wider
  edge row a walk must read past.

## 4. Plan, delegation, revision, invalidation

| PROV | definition (PROV-DM) | ours |
|---|---|---|
| Plan | "a set of actions or steps intended by one or more agents to achieve some goals", the third argument of an association | the instruction and doctrine a session ran under: `doctrine_sha256`, `skill_versions`, `config_revision_id`, and an entry's instruction hash |
| Delegation | authority and responsibility assigned to an agent, the delegator keeping some | the subconscious writes the decision the conscious recorded ([notebook-memory-types/00](../notebook-memory-types/00-design.md) §5) |
| Revision | "a derivation for which the resulting entity is a revised version of some original" | `superseded_by`; an entry's `base_revision_id` chain |
| Invalidation | "the start of the destruction, cessation, or expiry of an existing entity by an activity" | closing a relation (`valid_to`), retiring or superseding it; never a delete |
| Primary source | derived from what someone with direct experience produced | evidence may cite only Record or Rollup items (§5) |

Recording the plan is what makes a session re-derivable: the same input,
the same plan and the same model name the same activity. A session row
without its plan is a PROV association with the plan left out, and it
cannot be replayed.

## 5. Where the graph goes further on purpose

1. **World time.** PROV times describe the provenance events (generated,
   used, invalidated). The graph also records when a statement is **true in
   the world** (`valid_from` / `valid_to`), Graphiti's second timeline
   ([40](40-prior-art.md)). PROV has no place for it and needs none: it
   describes the record, not the world.
2. **Contradiction.** PROV derivation is support only. `relation_evidence.role`
   also carries `contradicts`, so a dispute is a qualified influence against.
3. **No conclusion as evidence.** PROV allows any derivation chain. The
   graph refuses Notebook items as evidence (27 §4): a judgement may be
   derived *alongside* another (a link) but never *from* it (a citation), so
   a guess cannot cite itself and grow stronger. PROV can describe the rule;
   admission enforces it.
4. **Scope.** PROV has no read boundary. Every row here carries its unit
   (DEC-231), and a walk never crosses one.

## 6. Validity rules we already hold, in PROV's terms

PROV-CONSTRAINTS orders events: an entity is generated before it is used,
and generated before it is invalidated; an activity starts before it ends.
The graph's matching rules:

| PROV-CONSTRAINTS | ours | enforced by |
|---|---|---|
| generation precedes usage | a backfill item may read only what existed at its own time | the walk's `valid_at`; `test_backfill_walk_excludes_relations_after_items_time` |
| generation precedes invalidation | a correction closes a relation no earlier than it began | **not checked**: `memory_admission` admits a `close` whose `at` precedes the relation's `valid_from`, which would hide it at every time (below) |
| usage only of what was shown | evidence must name a source the session was shown | `unseen_source` refusal |

**The one gap: `used` is a receipt, not a link.** What a session was shown
is kept as the `shown_sources` receipt of that session, as JSON.
"Which sources did the session read when it wrote this relation?" is
answered by reading receipts, not by a walk. The spike's relation judge
already needs exactly this answer. Not built: nothing has failed without it.
`# ponytail:` its upgrade is a `used` side record per session (session →
source key), written with the session, and a walk from `written_by` to it.
Build it when a read path, the answer gate or a dispute needs it.

**A second gap: a close may precede its start.** Admission checks a
correction's target, scope and evidence, never its time, so a `close` dated
before `valid_from` leaves a relation that no `valid_at` walk returns: a delete
by another name, which 27 §4 forbids. No such row has been seen. The guard is
one comparison in admission, worth adding once the spike's rerun shows step 1
writing corrections at all.

## 7. Bundles and alternates

- **Bundle** ("a named set of provenance descriptions, and is itself an
  entity"): a Cognition session with its receipts is one. So is the spike's
  frozen sample, whose hash is fixed before any model call, and the design
  graph's own `provenance: asserted` edges. Provenance of provenance is what
  lets a verdict be checked without trusting its producer (CMS rule 3).
- **Alternate / specialization:** one person is one pointer entity **per
  unit** (27 §3). Each is a specialization of the authored identity in
  `identity.toml`, scoped to one unit. `same_as` is stronger than PROV's
  alternate: it merges two entities into one.

## 8. What this node does not decide

- No RDF, no triple store, no PROV-O export. One renderer would add it if an
  audit ever asks for one (§1).
- No rename of tables or columns to PROV's names.
- The `used` record (§6) is not built.

**This holds unless** a provenance question the graph must answer turns out
to need a PROV concept with no row here (for example qualified usage with a
role per source), which would make §6's gap the next build.

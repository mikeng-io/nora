Why session lives in ./state/

  • Pairing = account credentials — losing it loses the link, not history.
  • Deliberately not under ./data: Nora must not read transport credentials. Same wall as ./state/signal-cli.
  • One place to look, back up, restore; never commit.

Pairing (first run only)

  • docker compose run --rm whatsapp-bridge --pair → QR (refreshes ~20s).
  • Scan from bot number: Settings → Linked Devices → Link a Device.
  • Session persists; boot never re-scans. Re-pair = same command.

06

Ban-risk contract

the core caveat
Posture: WhatsApp does not officially support third-party bots outside Business API. Unofficial bridge → small risk of account restrictions. Running rules below keep it acceptable.

Rules that make it viable

  • Dedicated number — never a personal one (largest single risk cut).
  • Reply-only, conversational — no bulk, no broadcasts, no outbound to people who didn't message first. Nora is silent by default; the design already enforces this shape.
  • No scheduled/bulk campaigns through the bridge, ever. That need → Business API conversation, not this one.
  • Accept protocol churn — WhatsApp Web updates break bridges; fix = bump Baileys pin, rebuild, re-pair. Maintenance cost, not architecture.

Failure modes

  • Protocol update → reconnect loop / messages stop → bump pin, rebuild, re-pair.
  • Phone offline >14 days → device unlinked → re-pair.
  • Session dir corrupt → auth error at boot → re-pair (DB is the record).
  • Account restricted → login throttled → stop using the number, evaluate cause.
  • Network blip → auto-reconnect (Baileys scheduler).
